# Known Limitations and Open Release Gates

This is the current as-built limitation list. Validation limitations are
separated from intentional product/platform constraints. Historical test counts
do not convert an unverified current behavior into a pass.

| Limitation | Cause / category | User or operator impact | Current behavior / workaround |
| --- | --- | --- | --- |
| Offline revocation is not immediate | Offline/Firebase architecture | A disconnected client cannot learn that a remote pair was revoked and may retain cached data until reconnect. | Cached data remains marked with age; next remote requests are checked by Rules. Reconnect/two-client scenario is NOT TESTED end-to-end. |
| No server-side pairing rate limit or global pair-ID uniqueness | Spark-only architecture | Authenticated clients are not server-throttled; a modified client could attempt extra pair documents. | CSPRNG short-lived codes, unlistable/single-use code rules, two-member pair rules and membership immutability mitigate access; no server-grade rate-limit claim. |
| No App Check | Backend configuration not implemented | No App Check attestation gate exists for clients. | Firestore Rules remain the authorization boundary; App Check is not a substitute for Rules. |
| No scheduled cross-user retention/cleanup | Spark-only architecture | Old records may remain until an owner-scoped operation occurs. | Owner-controlled deletion/lazy cleanup only; no Cloud Scheduler or privileged server. |
| Existing history is not retracted when a category is later disabled | Data model/security design | Previously authorized minimized events can remain as historical records while pair authorization continues. | Current reads remain owner/pair authorized; disabling sharing gates future state/event access according to Rules. See security doc for category-history semantics. |
| Android collection/background work is best effort | Android OS/manufacturer restrictions | Observations and listeners can be delayed or stopped when backgrounded, suspended or terminated. | Resume triggers a new observation/sync where possible; no continuous/24-hour monitoring promise. |
| Physical power-off is not observable | Android platform | App cannot reliably state the device was powered off. | Uses active/recent/offline/unknown reachability and last-seen time only. |
| Location is foreground-only and may be approximate/stale | Permission/platform/privacy decision | No background location and no guaranteed precise/current fix. | Shows availability, accuracy/freshness; asks for OS permission only in feature context. |
| Charging duration can lose continuity | Collector implementation | Process restart or observation gap can make the continuous duration unknown/reset. | Duration is derived from observed transitions, not guessed across gaps. |
| Notifications are local and best effort; no remote push | Spark-only architecture/platform settings | Partner does not receive a server push; local Android alert can be denied/disabled/suppressed. | Generic Android notification, `Rule alerts` channel; rule match alone does not guarantee delivery. |
| Notification deduplication is process-local and tap flow is unvalidated | Implementation/validation | Restart behavior and authorization after tap are not yet demonstrated on device. | Current auth/pair providers remain the source of access; device/release tests are BLOCKED. |
| No password-reset or account-deletion UI/flow found | Current auth feature scope | Users do not have these self-service flows in the app source. | Decide product policy and provide a verified support process before distribution if required. |
| No central crash/analytics monitoring | Privacy/Spark scope | Maintainers do not get a remote crash dashboard or real-time operational alert. | Production logger is local and privacy-filtered; use Firebase Console and user reports, no remote telemetry claim. |
| Firebase production target is unconfirmed | Configuration/release | The source project may not be the intended production backend. | Current config points to `gendersocialapp`; verify ownership, plan, Auth and Firestore state before deployment. |
| Release identity and artwork still need release verification | Release configuration | Android ID is `com.aj.kam`; the Firebase client file is local/ignored; the supplied gold emblem is now used for Android launcher icons. | Verify the matching Firebase registration and icon rendering on target devices before distribution. Avoid changing the ID after distribution. |
| Release signing is not provisioned | Release operations | No signed distributable artifact can be produced in the current environment. | Gradle requires secure `KAM_RELEASE_*` values and has no debug-key fallback. Keystore/credentials were not found/configured. |
| Phase 26/27 validation is blocked | Tool/device/account environment | Current tests, emulator suite, Android install and two-user acceptance are unknown. | Flutter commands stalled, Firebase CLI/Node/npm unavailable, ADB directory creation denied, and no controlled devices/accounts were available. Do not treat historical phase passes as current. |
| Original SRS and Phase 20 completion report are absent | Repository documentation | Some original requirements/phase decisions cannot be independently traced from this checkout. | Use `REQUIREMENT_MAPPING.md`, implementation, Phase 20 recovery design doc and reports that exist; record missing provenance rather than inferring it. |
